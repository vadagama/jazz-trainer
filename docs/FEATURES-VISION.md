# FEATURES-VISION — Управление feature-флагами в админке

**Дата:** 2026-07-19
**Статус:** 🟡 Черновик — ожидает подтверждения
**Версия:** v1.0

## 1. Резюме (Executive Summary)

Сейчас механизм feature-флагов в Amazilia существует только на уровне бэкенда: таблица `feature_flags` в БД, функция `resolveFlags()` в `rbac.service.ts`, хук `useFlag()` на фронте. Флаги возвращаются клиенту через `/api/auth/me`. Но **управлять флагами нечем**: нет ни API-эндпоинтов для CRUD, ни UI в админке. Плагин `admin-flags` — заглушка с текстом «Feature flag management coming soon.». Чтобы включить или настроить флаг, разработчик должен лезть в БД руками.

**Цель:** построить полноценный раздел управления feature-флагами в админке, позволяющий администратору (роль `super_admin` / `admin`) создавать, редактировать, включать/выключать и удалять флаги, настраивать таргетинг (роли, пользователи, процентный роллаут) и видеть историю изменений — без прямого доступа к БД.

**Ключевая ценность:**

- **Для администратора:** «Хочу включить новый раздел "Мелодические диктанты" для 10% пользователей» → зайти в админку → создать флаг → выставить 10% → наблюдать метрики.
- **Для разработчика:** «Хочу задеплоить новую фичу за feature-флагом» → создать флаг через админку → использовать `useFlag('new-feature')` в коде → включить для всех после валидации.
- **Для продукта:** «Хочу A/B-тестировать новый UI каталога» → создать флаг с 50/50 роллаутом → собрать аналитику.

**MVP:** CRUD флагов через API + UI в админке, базовый таргетинг (enable/disable, роли, пользователи). Расширенный таргетинг (проценты, A/B-группы, расписание) — P1.

## 2. Текущее состояние (as-is)

### 2.1. Схема БД

```sql
feature_flags (
  key       TEXT PRIMARY KEY,   -- например 'new-catalog-ui', 'beta-exercises'
  enabled   INTEGER DEFAULT 0,  -- boolean: включён/выключен
  roles     TEXT,               -- JSON-массив ролей: '["super_admin","admin"]'
  userIds   TEXT,               -- JSON-массив ID пользователей: '["user-a","user-b"]'
  created_at INTEGER            -- unix timestamp
)
```

**Ограничения текущей схемы:**

- Нет поля `description` — администратор не видит, зачем флаг и что он делает.
- Нет поля `category` — флаги не сгруппированы (UI, эксперименты, фичи). При 20+ флагах список станет нечитаемым.
- Нет `expiresAt` — нельзя задать автоматическое отключение флага через N дней.
- Нет `createdBy` / `updatedBy` — нет привязки к администратору, создавшему флаг.
- Нет процентного роллаута (`rolloutPercent`) — только бинарный таргетинг (роль/пользователь).

### 2.2. Бэкенд

```
resolveFlags(db, userRole, userId) → Record<string, boolean>
```

Логика: для каждого флага проверяется `enabled`. Если `true` — проверяется `roles` (JSON-массив) и `userIds` (JSON-массив). Если фильтры не заданы — флаг доступен всем. Если заданы — совпадение по роли **или** пользователю даёт доступ.

**Что уже работает:**

- ✅ Чтение всех флагов из БД
- ✅ Резолюция для конкретного пользователя (роль + ID)
- ✅ Возврат флагов в `/api/auth/me`
- ✅ Permissions `flags:read` и `flags:write`
- ✅ Хук `useFlag(key)` на фронте

**Чего нет:**

- ❌ API-эндпоинты для CRUD флагов
- ❌ Валидация при создании/редактировании (Zod-DTO)
- ❌ Аудит изменений флагов (кто, когда, что поменял)
- ❌ Graceful handling: если `roles` содержит невалидный JSON — молча игнорируется (нет валидации при записи)

### 2.3. Фронтенд

Плагин `admin-flags`:

- Манифест: `id: 'admin.flags'`, `category: 'admin'`
- Маршрут: `/admin/flags` (requires: `flags:read`)
- Нав-секция: `'admin'`, лейбл `'Flags'`, иконка `'flag'`
- **Страница — заглушка:** `<h1>Admin — Feature Flags</h1><p>Feature flag management coming soon.</p>`

## 4. Новые функции (Features)

### 4.1. API CRUD для feature-флагов

- **Проблема:** Сейчас нет программного интерфейса для управления флагами. Администратор не может создать/изменить/удалить флаг иначе как через прямой SQL-запрос.
- **Описание:** Набор REST-эндпоинтов в `apps/api/src/routes/admin-flags.routes.ts`:

  | Метод    | Путь                    | Permission    | Описание                                                     |
  | -------- | ----------------------- | ------------- | ------------------------------------------------------------ |
  | `GET`    | `/api/admin/flags`      | `flags:read`  | Список всех флагов с фильтрацией (поиск, категория, статус)  |
  | `GET`    | `/api/admin/flags/:key` | `flags:read`  | Детали одного флага + история изменений                      |
  | `POST`   | `/api/admin/flags`      | `flags:write` | Создать новый флаг                                           |
  | `PATCH`  | `/api/admin/flags/:key` | `flags:write` | Частичное обновление флага (вкл/выкл, таргетинг, метаданные) |
  | `DELETE` | `/api/admin/flags/:key` | `flags:write` | Удалить флаг (soft delete — архивирование)                   |

  **Валидация:** Zod-DTO в `@jazz/shared`:

  ```ts
  const CreateFlagSchema = z.object({
    key: z
      .string()
      .min(1)
      .max(100)
      .regex(/^[a-z0-9._-]+$/),
    description: z.string().max(500).optional(),
    category: z.enum(['feature', 'experiment', 'maintenance', 'killswitch']).optional(),
    enabled: z.boolean().default(false),
    roles: z.array(z.string()).optional(),
    userIds: z.array(z.string()).optional(),
    rolloutPercent: z.number().int().min(0).max(100).optional(),
    expiresAt: z.number().int().positive().optional(), // unix timestamp
  });

  const UpdateFlagSchema = CreateFlagSchema.partial().omit({ key: true });
  ```

- **Приоритет:** P0 (MVP)
- **Усиливает / Новый модуль:** `apps/api` (новый роут-файл), `@jazz/shared` (DTO)
- **Зависимости:** Расширение схемы БД (4.2), аудит (4.5)

### 4.2. Расширение схемы БД `feature_flags`

- **Проблема:** Текущая схема минимальна и не поддерживает описание, категории, процентный роллаут, срок действия.
- **Описание:** Добавить колонки (миграция):

  | Поле             | Тип                                | Назначение                                                                                                                                                                                   |
  | ---------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `description`    | TEXT                               | Человекочитаемое описание: что включает флаг, зачем                                                                                                                                          |
  | `category`       | TEXT (nullable)                    | `'feature'` \| `'experiment'` \| `'maintenance'` \| `'killswitch'`                                                                                                                           |
  | `rolloutPercent` | INTEGER (0–100, default null)      | Процентный роллаут (null = не используется). Если задан, флаг возвращает `true` для указанного % пользователей на основе детерминированного хеша `hash(key + userId) % 100 < rolloutPercent` |
  | `expiresAt`      | INTEGER (unix timestamp, nullable) | Дата автоматического отключения флага. После этой даты флаг всегда возвращает `false`, даже если `enabled = true`                                                                            |
  | `createdBy`      | TEXT (FK → users.id, nullable)     | Кто создал флаг                                                                                                                                                                              |
  | `updatedAt`      | INTEGER (unix timestamp)           | Последнее изменение                                                                                                                                                                          |
  | `updatedBy`      | TEXT (FK → users.id, nullable)     | Кто последний изменил                                                                                                                                                                        |

  **Обратная совместимость:** Все новые колонки nullable или имеют default. Существующие флаги продолжают работать без изменений. `resolveFlags()` расширяется поддержкой `rolloutPercent` и `expiresAt`.

- **Приоритет:** P0 (MVP — поля description, category, createdBy, updatedAt обязательны; rolloutPercent и expiresAt — P1)
- **Усиливает / Новый модуль:** `apps/api/src/db/schema.ts`, `rbac.service.ts`
- **Зависимости:** Миграция БД (drizzle)

### 4.3. Админ-UI: страница управления флагами

- **Проблема:** Плагин `admin-flags` — заглушка. Администратор не видит список флагов, не может их создавать или редактировать.
- **Описание:** Полноценная страница `/admin/flags` с тремя режимами:

  **А. Таблица флагов (основной вид):**

  | Колонка     | Описание                                           |
  | ----------- | -------------------------------------------------- |
  | Статус      | 🟢/🔴 индикатор enabled/disabled + бейдж категории |
  | Key         | Уникальный ключ флага (моноширинный шрифт)         |
  | Description | Краткое описание (truncated)                       |
  | Targeting   | Чипсы: «👥 2 роли», «👤 5 users», «📊 30%»         |
  | Expires     | Дата окончания или «Бессрочно»                     |
  | Updated     | Дата последнего изменения                          |
  | Действия    | ✏️ Edit, 🗑️ Delete (с подтверждением)              |

  **Функции таблицы:**
  - Поиск по `key` и `description`
  - Фильтр по категории (feature / experiment / maintenance / killswitch)
  - Фильтр по статусу (enabled / disabled / expired)
  - Сортировка по key, updated, expires
  - Пагинация (если > 20 флагов)

  **Б. Кнопка «+ New Flag» → модальное окно / slide-over формы создания:**

  Поля формы:
  - `key` \* — текстовый ввод с валидацией (только `[a-z0-9._-]`, до 100 символов)
  - `description` — textarea (до 500 символов)
  - `category` — select: feature | experiment | maintenance | killswitch
  - `enabled` — toggle (выключен по умолчанию)
  - `roles` — multi-select из существующих ролей (super_admin, admin, user, catalog_editor)
  - `userIds` — input для ID пользователей (email-поиск, multiselect) — P1
  - `rolloutPercent` — слайдер 0–100% — P1
  - `expiresAt` — date picker — P1

  **В. Редактирование флага:**

  Та же форма, что и создание, но:
  - `key` заблокирован (нельзя менять)
  - Показывает историю изменений (последние 10 записей из `audit_log`)
  - Кнопка «Save» + индикатор успеха/ошибки

- **Приоритет:** P0 (MVP — таблица + создание/редактирование базовых полей; роли и пользователи — P0; проценты и дата — P1)
- **Усиливает плагин:** `admin-flags`
- **Зависимости:** API CRUD (4.1), DTO (4.1), общие UI-компоненты админки (таблица, форма, модалка)

### 4.4. Процентный роллаут (Gradual Rollout)

- **Проблема:** Сейчас таргетинг только бинарный: роль или конкретный пользователь. Нельзя включить флаг для 10% пользователей и плавно наращивать до 100%.
- **Описание:** Добавить поле `rolloutPercent` (0–100) в схему и логику резолюции:

  ```
  if rolloutPercent задан:
    bucket = hash(key + userId) % 100
    flag = bucket < rolloutPercent
  ```

  Алгоритм:
  1. Хеш от конкатенации `flag.key + userId` через детерминированную хеш-функцию (например, `cyrb53` или упрощённый вариант) → целое число.
  2. Взять остаток от деления на 100 → «корзина» пользователя (0–99).
  3. Если номер корзины < `rolloutPercent` → флаг включён.

  **Важно:** Один и тот же пользователь всегда попадает в одну корзину для конкретного флага (детерминизм). Это гарантирует консистентность: пользователь не будет видеть флаг то включённым, то выключенным между запросами.

  **Приоритет роллаута в `resolveFlags()`:**
  1. Если `enabled = false` → `false` (быстрый выход).
  2. Если `expiresAt` задан и просрочен → `false`.
  3. Если задан `rolloutPercent` → проверка корзины (роли и userIds не учитываются при активном роллауте).
  4. Если `rolloutPercent` не задан → проверка `roles` и `userIds`.

- **Приоритет:** P1
- **Усиливает:** `rbac.service.ts` (resolveFlags)
- **Зависимости:** Расширение схемы БД (4.2), UI для слайдера (4.3)

### 4.5. Аудит изменений флагов

- **Проблема:** Изменения флагов не записываются в `audit_log`. Невозможно узнать, кто и когда включил/выключил флаг.
- **Описание:** При любом изменении флага через API записывать событие в существующую таблицу `audit_log`:

  ```ts
  // action: 'flag.create' | 'flag.update' | 'flag.delete'
  // details: JSON с изменениями:
  {
    flagKey: 'new-catalog-ui',
    changes: { enabled: [false, true] }, // [oldValue, newValue]
    // ...
  }
  ```

  Использовать существующий `audit.service.ts` (`withAudit`), расширив его поддержкой action-типов для флагов.

- **Приоритет:** P1
- **Усиливает:** `audit.service.ts` (новые action-типы), API-роуты флагов
- **Зависимости:** API CRUD (4.1)

### 4.6. Интеграция с существующей системой разрешений

- **Проблема:** Формальное описание: флаги и разрешения — разные механизмы, но администратор должен видеть их взаимосвязь. Например, флаг может гейтить доступ к фиче, для которой нужно разрешение.
- **Описание:** В карточке флага (детальный вид) показывать связанные permissions (если есть). Это не обязательная связь в БД, а конвенция: флаг `new-catalog-ui` может требовать `catalog:read`. Отображается как подсказка для администратора.

- **Приоритет:** P2
- **Усиливает:** `admin-flags` (детальная карточка)
- **Зависимости:** Нет

### 4.7. Bulk-операции

- **Проблема:** При деплое новой версии администратору нужно включить/выключить несколько флагов одновременно.
- **Описание:** Возможность выбрать несколько флагов в таблице (чекбоксы) и выполнить массовое действие: включить, выключить, удалить (архивировать).

- **Приоритет:** P2
- **Усиливает:** `admin-flags` (таблица), API (batch endpoint)
- **Зависимости:** API CRUD (4.1)

## 5. Out of Scope (за рамками)

| Что                                                              | Почему не сейчас                                                              |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| A/B-тестирование со сбором метрик                                | Требует системы аналитики (события, конверсии), которой пока нет              |
| Сегменты пользователей (groups) как альтернатива ролям           | Текущей RBAC-модели достаточно. Вернуться, когда появится >1000 пользователей |
| Зависимости между флагами («флаг A требует флаг B»)              | Усложняет модель без явной потребности на текущем масштабе                    |
| SDK для серверного использования флагов (не только resolveFlags) | Используется только в API и на фронте — текущего механизма достаточно         |
| Расписание включения/выключения (scheduled flag toggles)         | Покрывается `expiresAt`. Точное расписание — избыточно для MVP                |
| Webhook-уведомления при изменении флага                          | Нет потребителей. Вернуться при появлении CI/CD-интеграции                    |

## 6. Риски и допущения

| Риск / Допущение                                                                                                               | Уровень | Митигация                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------ | ------- | ---------------------------------------------------------------------------------------------------------------- |
| **[assumption]** Администраторов 1–3 человека. UI не требует сложной multi-user синхронизации (optimistic locking)             | Низкий  | Если количество администраторов вырастет — добавить optimistic locking на `updatedAt`                            |
| **[assumption]** Количество флагов не превысит 100 в ближайший год. Пагинация и поиск — достаточны                             | Низкий  | Архитектура таблицы масштабируется до 1 000+; добавить виртуальный скролл при необходимости                      |
| **Риск:** Детерминированный хеш для процентного роллаута может дать неравномерное распределение на малых выборках              | Средний | Использовать качественную хеш-функцию (cyrb53). На 100+ пользователях распределение близко к равномерному        |
| **Риск:** Миграция БД добавляет колонки — нужна обратная совместимость                                                         | Низкий  | Все новые колонки nullable с default. Код читает старые записи без ошибок                                        |
| **[assumption]** Флаги резолвятся только на бэкенде и в `/api/auth/me`. Не нужен SSE/WebSocket для real-time обновления флагов | Низкий  | Пользователь получает флаги при загрузке приложения. Изменения применяются после рефреша / следующего `/auth/me` |

## 7. Метрики успеха

| Метрика                             | Цель                                       | Как измерить                                           |
| ----------------------------------- | ------------------------------------------ | ------------------------------------------------------ |
| Время на создание флага             | < 30 секунд                                | От клика «New Flag» до сохранения в БД (измерять в UI) |
| Время на включение/выключение флага | < 5 секунд                                 | От открытия карточки до клика «Save» по toggle enabled |

| Отказ от прямого доступа к БД       | 0 ручных `INSERT/UPDATE` в `feature_flags` | Опрос команды через 2 недели после запуска             |
